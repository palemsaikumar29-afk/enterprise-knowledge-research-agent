# Trade-off Analysis — Enterprise Knowledge Research Agent

**Interview Kickstart — Applied Agentic AI, Week 1**
**Author: Sai Kumar Palem**

Every row is a real tension in this design. The columns record what we leaned toward, what we deliberately gave up, and why that choice is right *for this enterprise research setting* — the reasoning would differ for a consumer chatbot or a code agent.

| # | Decision area | We lean | We gave up | Why it's right here |
|---|---|---|---|---|
| 1 | **Planning: graph vs free-form LLM agent** | Hybrid — deterministic graph backbone for known flows, LLM reasoning only at decision nodes | Full ReAct-style free planning, which adapts to anything | Enterprise queries are semi-structured (decompose → retrieve → synthesize repeats constantly). Graphs are inspectable, testable, and cheap; LLM freedom is spent only where adaptation pays. Bounded, auditable behavior matters more than maximal flexibility when answers carry citations and compliance weight. |
| 2 | **Orchestration: single loop vs multi-agent swarm** | One orchestrator running Plan → Act → Observe | Parallel specialist sub-agents researching independently | A single loop keeps the evidence log, budget, and permission scope in one place — one trace to audit, one budget to enforce, one permission context to get right. Swarms complicate all three and multiply cost. Parallelism happens *inside* Act (batched tool calls), not across agents. |
| 3 | **Retrieval: pure vector vs hybrid** | Hybrid — BM25 + dense vector + recency weighting, cross-encoder rerank | Pure semantic search simplicity and lower infra cost | Initiative names, team names, and acronyms ("Project Beacon") are keyword-exact; paraphrases ("ways we tailor the homepage") need semantics; the 2-year freshness rule needs recency. No single signal covers all three. The infra cost is justified because retrieval quality is the ceiling on answer quality. |
| 4 | **Freshness: hard cutoff vs soft weighting** | Both — hard 2-year cutoff at retrieval, recency weighting within the fresh set | Soft weighting alone, which is simpler | The business requirement is a *rule* ("not older than 2 years"), not a preference. A rule enforced at retrieval time can never leak stale evidence into a citation; weighting alone would let a highly-relevant 2021 doc anchor a claim. Rules beat preferences where compliance is involved. |
| 5 | **Permissions: pre-filter vs post-filter** | ⭐ **Pre-filter at retrieval** — unauthorized docs never enter the candidate set | Post-filtering retrieved results, which is easier to bolt onto an existing index | Post-filtering means restricted content already touched the model context, the cache, and the trace — a leak with extra steps. Pre-filtering is structural: the query executes against the authorized subset only. Harder to build (ACL-aware index), but it is the only option consistent with "zero permission leaks." |
| 6 | **Caching: aggressive vs permission-scoped** | Permission-scoped caches (key includes permission-scope hash) | Global result cache with maximum hit rate | A global cache would serve one user's authorized view to another user — a direct violation of the zero-leak guardrail. We trade hit rate for safety; within a scope, repeated queries (common in follow-ups) still hit. |
| 7 | **Grounding: cite-or-abstain vs fluent completion** | Cite-or-abstain — every claim anchored or omitted | Fluent, confident-sounding answers with partial citation | In enterprise research, an uncited confident claim is a liability (wrong roadmap decisions, compliance exposure). Abstention with an explicit "could not verify" section is honest and debuggable; fluency without grounding is the failure mode we're designing against. |
| 8 | **Cost: best model everywhere vs routing** | Model routing — small/fast model for planning and Observe steps, large model only for final synthesis | Uniform top-tier model, simpler ops and best single-step quality | Cost per query is a Finance requirement, and planning/observation steps don't need frontier reasoning. Routing cuts cost ~5–10× on the loop steps while keeping synthesis quality where the user actually sees it. The trade is prompt-maintenance across two models — acceptable. |
| 9 | **Latency: sync-only vs pattern choice** | Three patterns — sync (≤8s), streaming (10–30s with live progress), async (long reports with job status) | One simple sync path | The 8s average target and the progress-indicator requirement can't both be met by one pattern: broad research genuinely takes longer than 8 seconds. Streaming keeps perceived latency low with honest step updates; async gives long work a real status endpoint instead of a timeout. Complexity in the orchestrator buys honesty in UX. |
| 10 | **Memory: session-only vs session + long-term** | Session memory now (follow-ups work at v0); long-term memory (glossary, corrections, past answers) at v1 | Full long-term personalization from day one | Long-term memory is permission-sensitive (a correction learned from restricted docs must not leak) and needs eval before it compounds. Session memory already satisfies the follow-up requirement; long-term memory ships once its scoping and eval are proven. |
| 11 | **Eval: human-only vs LLM-as-judge** | Both — golden set with human labels, LLM-as-judge for scale with bias controls | Human eval only (gold standard but unscalable) or judge-only (scalable but biased) | 300 queries/day can't be human-graded; judge-only drifts. The golden set (~50 growing to ~500) anchors the judge, and bias controls (position shuffling, reference-based scoring, periodic human spot-checks) keep it honest. |
| 12 | **Autonomy: open-ended vs bounded loop** | Bounded — step/depth limits, per-query budget cap, no-progress termination | Open-ended research that keeps digging until "done" | Open-ended loops fail expensively (cost runaway) and dangerously (confident hallucination after 40 steps). The budget cap doubles as the Finance requirement's enforcement mechanism. Bounded autonomy is the difference between an agent and a liability. |

## The starred row

**Row 5 (permissions pre-filter)** is the decision everything else depends on. If permissions were post-filtered, the trace, the cache, the memory, and the model context would all become leak surfaces, and every other guardrail would be compensating for that original sin. Structural security at retrieval time is the cheapest place to get this right and the most expensive place to get it wrong.

## What we'd revisit at 5,000 users

- **Row 8 (model routing):** as volume grows 5×, the savings compound — revisit with distilled/fine-tuned small models for the loop.
- **Row 6 (caching):** more users → more distinct permission scopes → lower hit rates; consider scope-hierarchy caching (a result authorized for "all employees" is safely shareable).
- **Row 10 (memory):** long-term memory becomes the main quality lever once per-query retrieval is tuned; its permission scoping must be proven before it scales.
